# Standing rules for this repository (from the owner)

- **Parity:** PHP_MySQL_Version and NODE_MySQL_Version must always behave the same. Every change goes into both.
- **Verify before pushing:** PHPUnit, Jest and the Playwright e2e suite (`e2e/`) against both stacks.
- **Ask before pushing:** never push to git without asking the owner first (this replaces the earlier "push always" rule, 2026-10-27).
  - When asking, first give a short summary: what is being pushed, which files change, and which functionality is affected.
  - With it, give the owner a **review pack** they can actually check before deciding (2026-10-28): (1) what changed, in plain words, one line per fix; (2) before/after screenshots on both stacks for everything visible; (3) "try it yourself" steps — which user/role, which order, what to click, what should happen (and what should now be refused); (4) which roles are affected; (5) test results on both stacks, failures explained; (6) risks and what was deliberately not changed; (7) live-site steps (migrations, in order); (8) files changed, grouped; (9) the decision asked: push / don't push / change first.
- **No PDF / document changes without double confirmation.** Before changing anything that ends up in a generated document (PDF or DOCX templates, the document data assembler, document builders), first show the owner what the document shows now and what it will show after the change, and get their confirmation twice. All current PDFs are correct as they are.
- **Standard and Kanban templates stay parallel (2026-11-01, hard rule).** Any user may pick either template, so both must offer the same functionality, screen for screen: every filter, search, count, field, badge, action, link and money rule on a Standard list page is on its Kanban board too, and the other way round. Every change to one template goes into the other in the same change, on both stacks, with tests (`KanbanParityTest` / `kanbanParity.test.js` enforce it).
- **Mockups first:** for a larger UI redesign, show mockup images and get confirmation before building.
- **CAFIN must never reach the client**, at any cost: not by download, link, email or portal.
- **Browser-side validation on every form, existing or new.** Every input form is checked in the browser before it is submitted, with the message shown beside the field (server-side checks stay as well).
  - The check lives once, sitewide, in `public_html/assets/js/app.js` (PHP) and `public/js/app.js` (Node). Every layout loads it. Extend `fieldError()` there for a new rule rather than writing per-page scripts.
  - Use HTML attributes (`required`, `type`, `min`/`max`, `minlength`, `pattern`) for the simple rules. `app.js` shows their messages inline and opens a closed step card that holds the invalid field.
  - A "Re-enter ..." field must be checked against the field it confirms. Name it `<name>_confirm` (or `confirm_password` for `new_password`), or give it `data-match="<name>"`. `FormValidationConventionsTest` / `formValidationConventions.test.js` enforce this.
- **Placeholders on every input (2026-11-01).** Every typed input and textarea, existing or new, shows a placeholder with an example or the expected format (not on date, file, checkbox, radio or hidden fields). `FormPlaceholderTest` / `formPlaceholder.test.js` enforce it; labels, the required "*" and "Choose…" on required drop-downs are enforced by `FormLabelConventionsTest` / `formLabelConventions.test.js`.
  - **Compact fields count as labelled (2026-11-13, D-366, owner: "do not ask me ever again").** A required field in a compact table row or a single inline box, identified by its column heading, placeholder or aria-label, needs no extra visible label or "*". Never flag or raise this again.
- **Never re-ask a decision already made (2026-11-13, owner, HARD RULE).** Before raising any question, check `docs/decisions/owner-decisions-register.md` (and CLAUDE.md). If the owner has already decided it, follow that decision and do not ask again, in QA rounds, reviews, audits or anywhere else. The only exception is when following the decision would cause a real loss (money, legal, data or security). Then ask, and always quote the earlier decision: its D-number, its date, what was decided and why it was decided then.
- **MySQL compatibility:** the host runs MySQL, while dev runs MariaDB. Never use `ADD/DROP/CHANGE COLUMN IF [NOT] EXISTS` or `CREATE INDEX IF NOT EXISTS`. Guard with information_schema + PREPARE instead (see `docs/migrations`). Queries must pass ONLY_FULL_GROUP_BY.
  - **phpMyAdmin on the shared host (2026-11-13, D-371):** the live site runs migrations in phpMyAdmin, which refuses the information_schema + PREPARE guard ("#1044 Access denied … information_schema"). A migration that adds columns uses plain `ALTER TABLE … ADD COLUMN` statements marked `PLAIN ALTER (owner D-371)` in its header (a second run only stops with "#1060 Duplicate column name", which is harmless); other migrations use plain UPDATE / INSERT … WHERE NOT EXISTS with no PREPARE. Every migration gets a row in the read-only check script, which the owner runs first.
- **SOP:** edit `docs/SOP`, then copy it to `PHP_MySQL_Version/docs/SOP` and `NODE_MySQL_Version/docs/SOP`.
- **Every money record has a correct description (2026-10-31, hard rule).** Every payment received or made, bill, expense, cost, payout, refund, export benefit and journal carries a description, in the app and in Zoho, that says what it is (advance / balance / freight / LC / supplier advance / CHA final / incentive / benefit …), for which order and party, what it settles (invoice / bill / claim / payout no.), and the bank reference (UTR / SWIFT / FIRC / scrip no.) whenever money moved through a bank. The app builds the description from the facts, so it is never blank or wrong; staff notes add to it, never replace it. A form that records money refuses to save without the bank reference where one exists. A new money flow is not done until this holds, with tests checking the exact wording on both stacks. Audit and fix list: register D-212.
- **Zoho change log (2026-10-29, always):** every change made in Zoho (Books, Mail, CRM, API Console, any Zoho One app), by anyone, manual or by script/API, test or real, gets a row in `docs/zoho/zoho-change-log.csv` (UTF-8 with BOM so Excel opens it cleanly) at the time it is made. Columns: Log ID (Z-001…), date & time IST, done by, on whose instruction, how (manually in Zoho / Zoho API script / our app's sync), Zoho app, organisation/account, where in Zoho (navigation path or API endpoint), action, what exactly (record, name/number, Zoho ID), value before, value after, why, test or real data, must be removed before go-live, removed on/by, related change in our app, owner approval, notes. Read-only checks get a row too ("Read only - no change"). Records our app creates automatically on the live site stay in its own Zoho Sync Log; while testing, every record created in Zoho is also logged here. Test records start with `TEST-` and are removed before go-live (removal logged here).
- **No PII anywhere (2026-11-06, STRICT HARD RULE).** No personally identifiable information in any file: no real person's name, e-mail address, phone/mobile number, personal address, personal ID numbers (PAN/Aadhaar/passport) or signature image named after a person — in documents, SOPs, READMEs, guides, registers, plans, mockups, samples, seed data, tests, fixtures or code comments. Always use role names and placeholders: "Managing Director" / md@email.com, "Executive Director" / ed@email.com, "Admin" / admin@email.com, company e-mail info@email.com, phone +91-0000000000. Real values are entered only on the live server at installation (the SQL block in each README, or Admin). Applies to new and existing text; any occurrence found is fixed at once.
- **Application Handbook stays current (2026-11-06).** `docs/APPLICATION_HANDBOOK.md` (copied to both stacks) is the single self-contained description of the application and the input for future development. Every change that adds or changes a feature, rule, setting, table or screen also updates it, in all 3 copies, in the same commit.
- **Tutorial videos follow the app — ask first (2026-11-07, HARD RULE).** The tutorial videos (`tutorials/`, catalogue and status in `tutorials/VIDEO_PROGRESS.md`) must match the app. Whenever a change alters anything a recorded video shows or says (a screen, field, wording, number, rule or step), first list the affected videos and what would change in each, and **ask the owner whether to update them** before re-recording. Never re-record silently, and never leave a known mismatch unreported. Re-recorded videos are sent to the owner as replacements and marked in `VIDEO_PROGRESS.md`.
